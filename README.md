# StroyControl

Платформа цифрового управления строительством — единая система контроля объектов,
задач, документов и финансов для CloudPlus.

Основано на ТЗ «Платформа цифрового управления строительством "StroyControl"»,
г. Ташкент, версия 1.0 (15.06.2026).

## Структура репозитория

```
stroycontrol/
├── backend/     — API-сервер (Node.js + TypeScript + PostgreSQL)
├── web/         — веб-интерфейс (React + TypeScript)
├── mobile/      — мобильное приложение (iOS/Android, кроссплатформенное)
└── docs/        — архитектура, схема БД, RBAC, окружения
```

## Быстрый старт (backend)

```bash
cd backend
cp .env.example .env       # укажите DATABASE_URL вашей PostgreSQL
npm install
npx prisma migrate dev     # создаёт схему БД
npm run prisma:seed        # демо-объект с задачами (опционально)
npm run dev
```

Тесты (нужна отдельная тестовая БД, см. `backend/.env.test.example`):

```bash
cp backend/.env.test.example backend/.env.test   # укажите тестовую БД
cd backend && npm test
```

## Быстрый старт (web)

```bash
cd web
npm install
npm run dev
```

## Локализация

Интерфейс поддерживает русский и узбекский языки (см. `web/src/i18n`).

## Статус MVP

Стабильная база этапа 1 зафиксирована и проверена 18.08.2026. Подробный протокол:
[docs/MVP_STAGE_1_AUDIT.md](docs/MVP_STAGE_1_AUDIT.md).

Реализованы авторизация и сессии, компании и RBAC, аудит, объекты и планирование,
задачи, фотоконтроль, документы, загрузка файлов, уведомления, лента событий,
mobile API, Android-клиент с офлайн-синхронизацией и web-клиент RU/UZ.

Изоляция компаний в рабочем API определяется только проверенной сессией.
Заголовок `x-company-id` разрешен исключительно интеграционным тестам и не
используется в production.

До выпуска MVP-кандидата остаются функциональная приемка web по ролям,
доработка найденных UX-дефектов и развертывание проверенного Vite-клиента.
Финансы, склад, камеры, 1С, банки, электронная подпись и AI не входят в MVP.

## Исторический статус этапа 0

**Этап 0** (подготовка): архитектура, схема БД, RBAC-модель, CI/CD-конфигурация,
скелеты backend/web, визуальный UI/UX-дизайн (`design/`) и демо-APK
(`mobile/stroycontrol-demo/`) — выполнены.

Не выполнено в рамках Этапа 0 (требует решений/доступов заказчика, не может быть
сделано автоматически):
- Подписание ТЗ заказчиком (раздел 20 ТЗ)
- Выбор и оплата реального облачного провайдера, домена, S3-хранилища
- Финальный UI/UX в Figma (сделан HTML/CSS-каркас с иконками и анимацией)

**Этап 1** (MVP) — в разработке:
- ✅ Модуль «Объекты и план-график» (`backend/src/modules/objects/`) — REST API:
  CRUD объектов с созданием из шаблона (типовой дом / многоэтажка / ремонт),
  вложенные этапы/разделы/задачи, расчёт прогресса и статуса риска
  (`on_track` / `risk` / `overdue`) по датам и статусам задач, эндпоинт
  `/api/objects/:id/gantt` для диаграммы Ганта. Покрыто тестами
  (`backend/tests/objects.test.ts`).
  - Мультитенантность реализована через обязательный заголовок `x-company-id`
    — это временная заглушка до полноценной аутентификации (JWT + сессии),
    которая ещё не реализована.
  - Автоматический прогноз сдвига даты сдачи по критическому пути (упомянут
    в ТЗ) пока не реализован — есть только точечный риск по задаче.
- ✅ Модуль «Задачи на объекте» (`backend/src/modules/tasks/`) — REST API:
  чек-листы, теги, приоритеты, ответственный (`assigneeId`), закрытие задачи
  с площадки с обязательными фото и геометкой (`/api/tasks/:id/close`),
  SLA-автоэскалация просрочки (`/api/tasks/sla-sweep`), повторяющиеся задачи
  (`/api/tasks/recurring-sweep`, пока только суточная периодичность). Покрыто
  тестами (`backend/tests/tasks.test.ts`).
  - Автоэскалация и повторяющиеся задачи реализованы как эндпоинты для
    периодического вызова (cron), а не фоновые джобы — планировщик (например,
    BullMQ, упомянут в ARCHITECTURE.md) ещё не подключён.
  - Реальная нотификация прорабу/ПМ при эскалации не отправляется — модуль
    «Лента и коммуникации» и Telegram-интеграция ещё не построены.
- ✅ Модуль «Фотоконтроль и технадзор» (`backend/src/modules/photocontrol/`) —
  REST API: фотоотчёты (progress / before / after / hidden_works) с гео-меткой,
  обязательная подпись инженера технадзора для фото скрытых работ, таймлайн
  прогресса по точке съёмки, журнал замечаний (дефект-лист) со статус-пайплайном
  open → in_progress → verified → closed. Покрыто тестами
  (`backend/tests/photocontrol.test.ts`).
  - Привязка фотофиксации к актам выполненных работ (формы РУз, раздел 6 ТЗ) —
    ждёт модуль «Документооборот».
  - Реальная загрузка файлов (S3) не реализована — API принимает уже готовый
    `fileUrl`; загрузка с устройства появится вместе с мобильным приложением.
- ✅ Модуль «Лента и коммуникации» (`backend/src/modules/feed/`) — REST API:
  сообщения по объекту, упоминания (`mentionedUserIds`), треды (ответы),
  реакции, поиск по тексту. Задачи и фотоконтроль автоматически публикуют
  системные события в ленту (закрытие задачи, смена статуса замечания).
  Покрыто тестами (`backend/tests/feed.test.ts`).
  - Поиск сейчас — простой `ILIKE`, не полноценный full-text (tsvector/GIN) —
    задел на будущее при росте объёма переписки.
  - Уведомления в Telegram/push (раздел 8 ТЗ) не реализованы — требуют
    Telegram Bot API интеграции, которая пока не подключена.
- ⏳ Не начаты: документооборот, кабинет заказчика, полноценное мобильное
  приложение (сейчас есть только визуальное demo-APK, см. `mobile/`).

**Этап 2** — не начат. Часть требует внешних решений ещё до реализации кода:
- Финансы и бюджет объекта — можно начать реализацию без внешних зависимостей
- Снабжение, склад, инструмент — можно начать реализацию без внешних зависимостей
- Видеонаблюдение — требует закупки/подключения реальных IP-камер (раздел 18 ТЗ:
  «поставка и монтаж камер оплачивается отдельно») — без этого можно построить
  только серверную часть (RTSP→HLS) без реального видеопотока
- Электронная подпись для документооборота — требует выбора и интеграции
  конкретного провайдера э-подписи (решение заказчика)
- Интеграция с 1С и банковскими выписками — требует доступов к этим системам
